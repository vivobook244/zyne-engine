# Phase 1.3 — Event System

**Status:** IMPLEMENTATION IN PROGRESS  
**Started:** 2026-11-04  
**Repository:** `vivobook244/zyne-engine`  
**Branch:** `main`

## 1. Goal

Establish a backend-independent event contract between the operating system, platform adapter, and runtime. Preserve event arrival order and keep OS event-loop mechanics out of runtime policy.

## 2. Ownership

- `zyne-platform` captures native events and translates them into ZYNE-owned `PlatformEvent` values.
- `zyne-runtime` owns the FIFO `EventQueue` and decides when queued events are consumed.
- `zyne-core` remains independent of platform, windowing, and event-loop types.
- The private winit adapter remains the only module that imports winit event types.

## 4. Event delivery contract

1. The winit adapter receives an OS event.
2. The adapter translates it into a `PlatformEvent`.
3. The platform handler callback receives the event on the event-loop thread.
4. Runtime-facing code may enqueue the event in `EventQueue`.
5. Runtime consumes queued events in FIFO order at a deliberate point in its host loop.

The queue is currently single-threaded and does not introduce worker threads or synchronization. Runtime host-loop integration and engine lifecycle decisions remain Phase 1.5 work.

## 5. Validation

Automated validation is expected through the repository CI workflow:

```bash
cargo fmt --all -- --check
cargo clippy --locked --workspace --all-targets -- -D warnings
cargo test --locked --workspace
cargo check --locked --workspace
cargo run --locked -p zyne-runtime --example headless_smoke
```

Manual platform event smoke test:

```bash
cargo run --locked -p zyne-platform --example window_smoke
```

Expected output includes a platform `Resumed` event after window creation, followed by window events such as resize, focus, scale-factor, redraw, and close request when generated by the desktop environment. `Suspended` is platform/OS dependent and may not occur during an ordinary desktop session.

## 6. Deferred

- Runtime application host and event queue integration into the engine lifecycle loop (Phase 1.5).
- Keyboard and mouse input event contracts/state (Phase 1.4).
- Frame scheduling and event-loop pacing (Phase 1.6).
- Multi-window event identity.
- Cross-thread event producers and synchronized queues; add only if a concrete subsystem requires them.
